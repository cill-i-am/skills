# Shared skills audit: 19 retained capabilities

Date: 2026-09-05. Repository: `cill-i-am/skills`. Baseline: `e6072592f3d64c411af81f1e07a653e38a1f1140`.

This is a recommendation-only audit of the 19 skills outside the 17-skill port. No audited skill, template, global configuration, memory, external service, or repository script was changed or executed by this pass. These recommendations are future work, not additional conditions for the current PR.

The review applies the guidance in [Eric Provencher's post](https://x.com/pvncher/status/2095991462416490862): assume a capable model, give a short discriminating trigger, reveal supporting material when relevant, specify outcomes and genuine constraints, and allow already-authorized work to continue. The recommendations below are judgments from the audited files, not claims that reducing their length has already improved model performance.

## Overall recommendation

Keep the 19 capabilities. Shared Linear planning, ownership, reconciliation, and delivery remain useful independently of Meal Planner. Their principal weakness is duplicated workflow policy and rigid routing, rather than an absence of useful knowledge. Consolidate repeated rules into the adopted repository policy; keep role entrypoints focused on their particular decisions. Do not automatically install that entire operating model whenever a user asks for a PRD, a lesson, or a handoff.

Preserve observable acceptance criteria, dependency relations, one mutation owner per scope, current review targets, truthful evidence, secret-safe reporting, and authority checks for actual external effects. Preserve independent review where requested or required by the adopted delivery policy; a shorter skill need not remove that safeguard. Qualify defaults with task context and existing authorization instead of introducing another permission cycle.

## Highest-value findings

1. **Continuation can be incorrectly stopped.** [handoff/SKILL.md:60](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/personal/handoff/SKILL.md#L60) tells the next agent to wait for new user instructions before making changes. The handoff can therefore suspend work the user already authorized. Carry forward the next action and its scope: “Verify the facts needed for the next action, then continue the authorized task; ask only about an unresolved decision or authority boundary.” The skill should also accept an inline handoff instead of always requiring a saved artifact and a duplicate fenced copy at lines 28–31.

2. **Generic orchestration is treated as task-creation authority.** [orchestrator/SKILL.md:23](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/execution-loop/orchestrator/SKILL.md#L23) states that asking to orchestrate a Project authorizes user-visible worker tasks. That is incompatible with runtimes whose user-owned task tool requires an explicit new-task request; the tool contract supplied in this session is one example. Say to dispatch using an available mechanism within current user and tool authorization. Keep native subagents distinct from user-owned tasks and scheduled automations. The skill cannot grant permissions on behalf of its host.

3. **A concrete statement about subagents is false in this host.** [subagent-execution/SKILL.md:39](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/execution-loop/subagent-execution/SKILL.md#L39) says subagents do not inherit context. This session's `collaboration.spawn_agent` contract defaults to inheriting all history. Replace it with: “Check what context the chosen mechanism shares; provide the missing scope, authority, inputs, and expected result.” This is a comparison with the provided runtime contract, not an executed delegation test.

4. **The template policy claims excessive precedence and sometimes discards prior authorization.** [execution-policy.md:8](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/execution-loop/linear-setup/assets/docs/agents/execution-policy.md#L8) presents itself as the highest authority while project instructions merely narrow it. A bundled template is subordinate to actual system, developer, user, and applicable repository instructions. At [execution-policy.md:92](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/execution-loop/linear-setup/assets/docs/agents/execution-policy.md#L92) and [worker-thread-template.md:38](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/execution-loop/linear-setup/assets/docs/agents/worker-thread-template.md#L38), credentials or real data independently trigger a stop even if their use is already authorized. Gate unauthorized access/effects, not the category alone. Keep separable local work moving while a genuine external step is blocked.

5. **Read-only or drafting requests can inherit publishing steps.** [to-prd/SKILL.md:35](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/execution-loop/to-prd/SKILL.md#L35) moves from broad product-spec triggers into updating/creating a Linear container and writing the PRD; Draft Mode is a special case at lines 54–59. [triage/SKILL.md:70](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/execution-loop/triage/SKILL.md#L70) and [to-prd/SKILL.md:83](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/execution-loop/to-prd/SKILL.md#L83) prescribe comments. Determine requested mode first: inspect/recommend, draft, or publish/update. Perform previously authorized writes without reconfirming them; do not infer messages to others from a request for a draft or status view. Keep the useful explicit no-mutation rules already in Wayfinder and orchestrator simulation mode.

6. **“Read-only” cyber checks can execute the suspect software.** [cyber-audit/SKILL.md:53](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/personal/cyber-audit/SKILL.md#L53) suggests `<binary> --version`. In the skill's malicious-package/supply-chain use case, invoking the suspect binary can execute its code; a version flag does not establish a read-only trust boundary. Prefer lockfiles, package/install metadata, trusted package-manager records, and the relevant process evidence. Only invoke software whose trust is established independently. This is a static risk finding; no suspect code was executed.

7. **Some personal skills capture much broader requests than their artifact workflow fits.** [teach/SKILL.md:3](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/personal/teach/SKILL.md#L3) includes “asks to be taught,” but lines 8–20 assume the current directory is a course workspace and lines 27–28 require a question before teaching. Restrict the persistent workspace mode to a multi-session learning workspace request. An ordinary explanation can be complete in the conversation. [youtube-transcript/SKILL.md:8](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/skills/research/youtube-transcript/SKILL.md#L8) similarly requires a local transcript file before any summary; save when useful/requested and keep temporary source material out of an unrelated repository.

8. **Existing scenario checks are not agent evaluations.** [validate-execution-policy.mjs:102](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/scripts/validate-execution-policy.mjs#L102) and [validate-discovery.mjs:120](https://github.com/cill-i-am/skills/blob/e6072592f3d64c411af81f1e07a653e38a1f1140/scripts/validate-discovery.mjs#L120) define small JavaScript functions and compare their outputs with hardcoded expected values. Those functions neither load instructions for model interpretation nor invoke an agent. Literal prose checks at execution-policy validator lines 18–37 and discovery validator lines 60–118 also penalize valid wording changes. Keep structural/link/package checks; label scripted examples honestly. If later measuring instruction quality, use a few realistic tasks with observed agent actions, including negative authority cases. No such model evaluation was performed here.

## Supporting resources and consolidation

The nine Linear setup documents all have actual callers from skill bodies or the document index. There is no defensible blanket “unused templates” deletion here. Retain an adaptable PRD template, issue template, worker/reviewer briefing examples, and a compact canonical workflow policy. The installation gate requiring every file is a separate choice from whether an individual reference is valuable.

- `linear-setup/assets/docs/agents/README.md:7–16` is a useful index. Lines 21–27 could point to optional capabilities without enforcing a lifecycle.
- `execution-policy.md:19–37,63–81,150–167` repeats a fixed four-phase, three-tier, seven-level framework. The useful rule is to verify the actual changed boundary with evidence matched to consequence. Make the numbered proof items a menu of possible evidence, not a sequence. Keep current-target review and explicit unresolved claims.
- `linear-workflow.md:8–16,23–31` mandates a Project/PRD, user-visible task, parent/child hierarchy, and review machinery together. Apply this when the repository deliberately adopts that operating model; allow a smaller issue shape when it carries the same necessary outcome/ownership/dependency information.
- `issue-template.md:11–16,40–50,63–70` can omit empty hierarchy, risk-tier, handoff, and follow-up sections. Keep acceptance, scope, relevant dependencies, and appropriate proof.
- `worker-thread-template.md:23–39` repeats refresh/setup/risk/tracer/PR/stop policy. A compact dispatch example needs the issue, approved starting state, ownership, acceptance/proof, and actual gates; reference the policy for the rest.
- `reviewer-thread-template.md:25–43` should prove the requested immutable target and inspect/repeat meaningful evidence. Resolving remote default is not always needed to review a specifically supplied commit. Read-only remains a useful role boundary.
- `domain.md:26–29,33–41` and both domain-modeling references already discourage empty scaffolding and duplicate truth. Keep those references, with the ADR threshold treated as a contextual default. No deletion is recommended.
